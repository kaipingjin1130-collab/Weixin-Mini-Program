状态：待开发。依赖：B02来源记录及证据接口可用。

## 给AI的执行指令

执行B03。先读[公共约束](../01-平台设计与公共执行约束.md)、B02实际数据结构和来源查询服务。实现案例卡、检查要点卡的候选生成、人工核查和审核闭环。复用旧治理生效值，不另做原工作台全部字段治理功能。

人工只处理异常、补充判断和候选审核；既有字段自动带入。调用模型必须走适配接口，真实数据外发遵守已有授权；没有可用模型时允许显式模拟结构测试，但不能宣布真实生成效果已通过。

## 页面

| 路由 | 内容 |
|---|---|
| `/quality` | 缺失、冲突、候选依据等分类数量与处理入口 |
| `/quality/issues` | 异常列表、来源和处理状态 |
| `/knowledge/drafts` | 草稿、待审、退回列表，批量生成入口 |
| `/knowledge/{id}/edit` | 左侧证据，右侧结构化知识卡与修改差异 |
| `/reviews` | 待办、退回原因、版本与审核操作 |

## 表

| 表 | 字段/约束 |
|---|---|
| quality_issues | record_version_id、rule_code、field、severity、status；同版本同规则问题去重 |
| record_annotations | record_version_id、field、value、source_kind、actor、reason |
| knowledge_items | type、title、scene_code、object_type、scope、current_revision |
| knowledge_revisions | item_id、version、content、schema_version、template_version、model_ref、state、row_version |
| knowledge_evidence_links | revision_id、claim_path、evidence_id、relation_type |
| review_actions | object_type/id/version、action、reviewer、reason、time |

review_actions是审核留痕；审核待办可由待审状态查询生成，接口review id必须有稳定映射，不伪造永远相同的ID。审核事务核对对象版本。

## 接口

前缀`/api/v1`：
`GET /quality/issues`、`PATCH /quality/issues/{id}`、
`POST /knowledge/generation-jobs`、`GET /knowledge`、`GET /knowledge/{id}`、
`PATCH /knowledge/{id}/draft`、`POST /knowledge/{id}/submit-review`、
`GET /reviews`、`POST /reviews/{id}/approve`、`POST /reviews/{id}/request-changes`。

生成请求明确来源版本、知识类型、模板及幂等键。批量范围先预览，不隐式选择所有项目。

## 实现细节

- 将事实、模型建议、人工确认分别标识。标准名称/条款/适用版本/核验状态不能混为一个文本。
- 卡片结构先用文件中的版本化Schema；B08再接管理页面。
- 模型输出先结构校验再保存，引用只能使用授权输入中的证据ID。
- 批量生成保留单项失败，人工确认内容不被重跑覆盖。
- 发布不是本任务职责，但approved对象必须可被B04消费。
- 模型不能自评通过审核；无证据的事实性主张不能批准为已核验知识。

## 验收标准

- [ ] 从已有记录生成候选卡，不要求重录项目、日期和描述。
- [ ] 模型返回不存在的证据ID时拒绝该引用并显示错误。
- [ ] “系统补充依据”保持待核验，不自动标为有效标准。
- [ ] 两人同时修改，旧row_version提交409。
- [ ] 审核操作关联准确版本；内容变更后旧批准不能复用。
- [ ] 重新生成不覆盖已人工审核内容。
- [ ] 无权限来源不能生成卡片；审核角色由服务端检查。
- [ ] 退回、修改、重新提交链路可操作并保留意见。
