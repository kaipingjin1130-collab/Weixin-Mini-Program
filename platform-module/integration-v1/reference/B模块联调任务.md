## 独立开发边界

B 的 AI 只修改 b-risk-knowledge 工程及 B 的文档、样例和测试；不得修改 A 的 server.py、host_auth.py、网页、PHP 桥接或数据库。A 的 AI 不修改 B 的 auth.py、前端和配置。两人分别使用独立分支/工作区和开发数据库，通过版本化 HTTP 合同协作。

账号、登录、项目成员和权限来源由 A 一人实现。B 的“身份接入”只是在 B 边界调用 A 的受控身份接口，把返回值转换为 Actor 并检查业务所需权限；不设计密码、身份签发或第二套账号。这项消费接口工作可用固定样例独立完成，无需 A 进入 B 目录修改代码。

首轮页面通过 A 的 /quality/b/ 入口同源访问：A 负责代理和当前会话，B 负责自己页面的基址、静态资源及路由兼容。两边不共同编辑导航文件、不开发跨站登录或 iframe 消息体系。

## 3. B-01：接入 A 身份和权限

### 修改位置

`backend/auth.py`、`backend/config.py` 及身份映射数据由 B 修改。A 只提供 HTTP 身份接口及样例，不修改上述文件。

### 实现方法与目标

1. 固定调用 `POST /integration/v1/identity/resolve`：携带 B 服务凭据及 A 代理传来的会话引用，取得 active、subject_id、org_id、display_name、projects（project_id 与 permissions），转换为 Actor。不解析 A 会话内部格式，不自行授予权限。A 不可用时返回依赖不可用，不放行或切换演示身份。
2. B 保留每个接口的服务端授权检查；不能因前端隐藏按钮或请求携带项目 ID 就视为有权。
3. 向 A 提交知识读取、加工、审核、发布、复盘操作、培训管理等权限需求，由 A 统一配置分配。
4. 用户访问和后台服务接入分别检查，不以服务身份绕过当前用户范围。
5. 正常页面移除模拟身份选择；显式测试环境可以保留。接入 A 退出、停用和撤权语义。
6. B 页面的浏览器请求走 /quality/b/，A 代理转发可信内部上下文。B 只接受已认证代理或服务调用，不信任浏览器自带身份 Header；无效会话 401、权限不足 403。A 负责登录与退出，B 提供返回 A 的界面，不做第二次登录。写请求经 A 的 CSRF 防护。

后台取件与用户查看分别处理：队列使用登记 B 服务身份读取获准成果，不依赖用户会话持续在线；用户查看 B 结果时重新核对当前权限。来源撤回按合同核对并阻断有效结果使用，不能因 B 已存有副本绕过撤回。

消费 A 已有 `GET /api/work/snapshot/{deliveryId}` 的原始冻结快照，不要求 A 改变响应外层；`GET /api/work/package/{deliveryId}` 可交接离线包。已有附件接口为 `GET /api/work/evidence-meta/{id}` 和 `GET /api/work/evidence/{id}`。B 服务访问上述接口的授权能力尚待 A 补齐，不把现有用户登录会话当作服务凭据。

新增目标是 `GET /api/work/delivery-meta/{deliveryId}`，返回 source_system、org_id、project_id、task_id、delivery_id、delivery_version、eligible、ineligible_reason、withdrawn、withdrawn_at、withdraw_reason。附件服务调用建议附带 `deliveryId` 查询参数，由 A 核对冻结成果成员关系。新增路径和参数须由 A 冻结合同；B 不能自行猜测。部署 /quality 时统一加前缀一次。取消此前另建整套 /integration/v1/deliveries 的要求。

## 5. B-03：按成果引用创建接入任务

以下均为建议新增接口，不是已实现接口；具体 Schema 由 B 在现有合同目录维护并交 A 使用：

| 接口 | 行为 |
|---|---|
| `POST /integration/v1/a-imports` | 按成果引用创建或复用接入任务，要求 `Idempotency-Key` |
| `GET /integration/v1/a-imports/{import_id}` | 返回接入状态、任务包回执、附件限制、复盘关联 |
| `POST /integration/v1/a-imports/{import_id}/retry` | 对允许重试的失败任务继续处理，要求幂等键和版本校验 |
| `POST /integration/v1/a-imports/{import_id}/withdraw` | 有权限且提供原因时撤回指定接入结果 |

创建正文：`source_system`、`project_id`、`task_id`、`delivery_id`、`delivery_version`。组织及权限从可信身份和来源登记获取，读取 A 元信息再次核对。

首次创建建议返回 202，重复请求返回原任务；响应至少包括 `import_id`、`status`、`status_url`、`replayed`。任务包生成后再关联现有 `receipt_id/job_id`，不要将它们与接入任务 ID 混为一谈。

### 实现方法

复用现有 Procrastinate 队列、任务恢复和业务事务模式：保存接入任务 → 获取 A 快照 → 转换校验 → 进入现有任务包服务 → 取件处理 → 更新结果。

- 按来源系统、成果 ID、成果版本建立业务唯一约束；幂等键相同但请求不同返回冲突。
- 保存每阶段结果、固定转换正文、内容哈希、重试次数和错误；响应丢失后重试返回原任务。
- 同一成果版本内容改变时报告冲突，不覆盖已接收事实。
- 区分暂时不可用、无权限、引用不匹配、合同失败和附件错误；永久错误不无限重试。
- 已被现有任务包服务接收时复用原回执和处理任务，不因外层重试再建包。
- 新版本失败不替换原可用版本，旧版本晚到不覆盖新版。
- 撤回沿用现有下游失效逻辑；补正产生新版，不自动抹除旧版。

### 验收

- [ ] 双击、超时、断点恢复不重复建包或产生重复复盘。
- [ ] 同版本异内容拒绝，旧版晚到不覆盖新版。
- [ ] A 停机、身份过期、取件失败有明确可恢复或终止状态。
- [ ] 状态查询仅对授权用户开放。

## 8. 执行顺序与交接
