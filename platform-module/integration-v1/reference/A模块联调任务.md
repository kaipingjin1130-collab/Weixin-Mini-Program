## 独立开发边界

两人各开一个 AI coding 会话、使用各自分支和开发环境。A 只能修改 A 仓库及 A 的接口说明、样例和测试；B 只能修改 B 工程及其接口说明、样例和测试。禁止让 A 的 AI 修改 B 的 auth.py，也禁止让 B 的 AI 修改 A 的网页或数据库。

原有功能归属不变：身份来源、账号和项目权限归 A，知识、复盘及培训归 B。服务端身份校验由 A 实现；B 只按固定 HTTP 合同调用结果并转换为自己的 Actor，不设计密码、令牌签发或账号体系。

首轮固定采用“浏览器只访问 A；A 后端代理 B；B 调用 A 校验身份及读取成果”的接入方式。B 页面在 A 的固定 /quality/b/ 入口访问，由 A 转发到 B；B 调整自己的静态资源、API 基址及路由以支持该前缀。避免首轮同时开发跨站单点登录、两套令牌交换或 iframe 消息体系。

| 范围 | A 的 AI 写权限 | B 的 AI 写权限 |
|---|---|---|
| A candidate、PHP 桥接、A 测试及文档 | 有 | 无 |
| B backend、frontend、contracts、B 测试及文档 | 无 | 有 |
| 对方接口 | 只消费固定版本合同；提出变更请求，不改对方实现 | 同左 |
| 数据库、配置、运行环境 | 各自独立，不共享可写开发数据库 | 各自独立 |

如两份工程在同一 Git 仓库中，使用不同分支或 checkout 并保持上述目录边界；不要让两个 AI 同时操作同一工作区。各模块负责人合并自己的改动，不相互覆盖整个目录。

- A 负责网页外层导航和原有巡查、整改、复核、报告、交接、归档流程。
- A 维护 A 提供接口的合同；B 维护 B 提供接口的合同及 A 数据适配、成果接入队列、附件取件、去重重试、知识、复盘与培训。没有双方同时编辑的公共合同文件。
- A 提供原始业务事实和受控接口；无需将自身快照改写成 B 合同，也不新增 B 接入调度系统。
- 本轮是网页联调；保持已有小程序接口兼容。

## 3. A-01：统一身份与权限（A 完整负责）

### 修改位置

- `host_auth.py`：复用原平台身份验证与账号映射。
- `server.py`：会话、身份桥接和接口授权。
- `QaxcAuthController.php`、`qaxc-route.php` 位于上级 `platform-module/`：仅在现有桥接不足时按需修改。
- 新增统一认证组件或身份校验接口，由 A 实现、维护并向 B 提供接入样例。

### 实现方法与目标

1. 稳定输出用户 ID、姓名、组织 ID、授权项目、项目角色和会话有效性，禁止以姓名作为身份主键。
2. 固定实现受控身份校验接口，避免两个 AI 分别选择认证方案。A 代理 B 请求时，将已验证的 A 会话引用通过专用内部 Header 转发；B 使用独立服务凭据回调 A，取得当前有效身份、项目范围及权限。A 必须剥离浏览器伪造的内部身份 Header；会话引用不得进入 URL 或日志。B 不解析 A 会话格式、不自行签发 A 身份。
3. 区分用户访问与 B 后台服务取件；服务账号只具有被授予的项目和成果访问范围，不默认拥有管理员权限。
4. B 提交知识加工、审核、发布、复盘、培训等权限需求；A 统一配置和分配，B 在自己的接口执行检查。
5. 停用、退出、项目移除和权限撤销后，按约定即时校验或撤销机制拒绝后续访问。若采用短期令牌，单靠令牌到期不能声称即时撤权。
6. B 页面经 A 的 /quality/b/ 同源入口访问，浏览器继续使用 A 会话；A 负责代理及会话失效响应，B 只负责其页面资源基址和路由。A 代理写请求沿用并验证 CSRF 防护；内部服务只能由可信调用方访问。A 不替 B 写前端或认证代码。

### 交接成果

身份接入说明、固定请求响应 Schema、可运行调用示例、正常/未登录/无权限/撤权样例、权限字典、测试账号与测试项目的获取方式、失效语义。凭据放在本机私有配置，不写入文档或仓库。

### A 提供接口的目标（现有接口优先复用）

- `POST /integration/v1/identity/resolve`：服务凭据＋会话引用，返回 active、subject_id、org_id、display_name、projects（project_id 与 permissions）。无效会话 401，服务凭据或范围不足 403，A 不可用时 B 返回依赖不可用，不放行。
- 已有 `GET /api/work/snapshot/{deliveryId}`：继续返回现有冻结快照，不改变原响应外层；为登记的 B 服务身份补充授权。已有 `GET /api/work/package/{deliveryId}` 可用于测试包交接及离线接入。
- 建议新增 `GET /api/work/delivery-meta/{deliveryId}`：单独返回 source_system、org_id、project_id、task_id、delivery_id、delivery_version、eligible、ineligible_reason、withdrawn、withdrawn_at、withdraw_reason。当前没有统一元信息接口，必须实现后才能声称在线资格及撤回可校验。
- 已有 `GET /api/work/evidence-meta/{id}` 和 `GET /api/work/evidence/{id}`：复用元数据及文件读取。对 B 服务调用要求携带 `deliveryId` 查询参数，并验证附件属于该冻结成果；保留已有用户调用兼容性。B 服务不带成果引用不得只凭项目权限下载。
- 后台取件使用已登记 B 服务身份的范围，不依赖创建任务的用户会话长期在线；读取 B 结果仍按当前用户权限检查。A 撤回来源后，身份/成果校验必须返回不可用语义，B 不得继续展示为有效结果。

A 在自己的工程维护接口 Schema、测试样例和校验脚本，并发布带版本的交接包。除明确标明已有的路径外，其余均待实现；新增元信息路径及 deliveryId 参数是建议，冻结实际合同后再开发。部署 /quality 时上述路径统一加该前缀一次。取消此前要求另建整套 /integration/v1/deliveries 读取接口的安排。

### 验收

- [ ] 用户在 A 登录后可进入 B，无须选择模拟身份。
- [ ] B 能识别同一稳定用户、组织和项目。
- [ ] 无权限项目、停用账号、撤权和无效会话均被服务端拒绝。
- [ ] B 服务身份不能冒充管理员或读取授权范围以外附件。

| B 目标接口 | A 调用方式 |

## 7. 顺序与交接

1. 接口先行：A 发布自己提供的 v1 接口说明、Schema、正常与异常样例；B 同时发布 B 的接口包。双方核对一次字段、状态和权限后锁定版本，不要求先完成服务。
2. 独立开发：A 用 B 的样例搭建本地替身，开发代理、页面和按钮；B 用 A 的样例开发身份消费和成果处理。双方都无需等待对方服务器上线。
3. 各自自测：提供方验证真实接口符合自己的 Schema；调用方验证对固定样例的处理。替身通过只算模块自测。
4. 合约联调：替换基址及私有凭据连接真实服务，核对身份、固定成果、附件和状态。接口不符由提供方修复，调用错误由调用方修复。
5. 页面验收：以 A 入口跑完整业务链、刷新/返回、前缀、撤权、重复提交与失败恢复。完成后分别提交自己的修改并记录版本。
