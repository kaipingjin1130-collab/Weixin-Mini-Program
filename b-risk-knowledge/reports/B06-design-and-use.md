# B06 过程复盘与经验：设计、使用与 AI 交接

本轮使用 B05 已有模拟任务包和 B02 模拟历史来源，未读取真实工程报告，未接真实 A、LLM 或训练模型。时间排序、配对时间差、期限对照、原文摘录均为确定性代码；建议使用明确标记的本地模拟模板。人工审核只是本地演示，不是实际工程签认。

## 直接试用

打开 Docker Desktop，双击项目根目录 `启动B模块.cmd`，进入 [过程复盘与经验](http://127.0.0.1:5181/retrospectives)。已有 B05 模拟吊装任务可直接选用，无需重复输入任务、事件、问题、期限和附件。

1. 选择“任务过程复盘”和一个已就绪的当前包，点击“生成复盘草稿”。B05 包详情也有“自动生成 / 更新复盘”和“打开已有复盘”。
2. 读取实际时间线，打开事件记录、模拟图片或日志附件。未知时间单列；历史案例不生成过程时间线。
3. 进入“核查与审核”。各条事实、记录对照和建议可以分别修改、确认；说明原因后保存新草稿版本。
4. 提交当前已保存版本审核；可从本页面或“知识加工与审核 → 审核待办 → 过程复盘”进入统一待办，执行退回/批准。批准要求逐条确认及整体证据确认。
5. 批准后点击“转为经验候选草稿”，打开知识候选继续核查、提交知识审核；通过后再到 B04 发布管理构建、启用。复盘批准、经验草稿、已发布知识是三种不同结果。
6. 切换“历史案例复盘”，选择同项目最多20条固定记录。只提供案例摘要及来源行，不能用隐患描述还原未记录的作业过程。

右上角模拟身份仍沿用 B01。加工员负责生成/编辑/提交/转草稿，审核员负责审批；学员不访问复盘加工区，只能访问 B04 已发布知识。演示管理员可验证完整链路。真实角色映射仍待 A 确认。

## 计算与证据边界

- 时间线使用来源实际时间；以时间、源数组位置、事件ID稳定排序。导出时间不代替发生时间。
- 时间差只在本任务唯一开始/结束事件均有实际时间且顺序有效时计算，名称为“开始至结束的记录时间差”，不等同有效工作量。缺时不补造。
- 期限规则位于 `scene-packs/generic/retrospective-v1.json`。演示规则只对登记场景、明确问题期限、已闭环快照、唯一有时间复核通过且为已知终态记录的情况比较时间。未知时间的后续整改/复核会阻断判断；没有期限、规则或可核对终态时显示“不判定”。这不是法律/规范上的超期认定。
- 流程对照显示“有记录/缺记录/不适用”。“缺记录”写“未发现相关记录”，不推断现场未执行；无问题且来源明确声明问题清单完整时，问题相关环节可为不适用。
- 事实须引用此固定版本证据；推断和建议单独标识。模型模拟部分不能自动批准。
- 当前同步处理限定为单包500条事件、100个附件以内，超出明确拒绝而不截断；历史模式最多20条。不将此实现宣称为大包或高并发能力。未来大包处理应复用 B01 队列，不增加第二套调度。

## 模块与数据库

| 文件/模块 | 职责 |
|---|---|
| `backend/modules/retrospectives/engine.py` | 无数据库副作用的排序、对照、时间与期限计算 |
| `schemas.py` / `service.py` / `api.py` | 固定来源、指纹去重、修订、统一审核与经验候选转换 |
| `sources.py` | 复盘证据适配、实时来源授权/撤回检查、检索前 SQL 过滤 |
| `frontend/src/Retrospectives.tsx` | 清单、两种来源选择、实际过程、逐项核查、审核及转草稿 |
| `migrations/versions/0006_b06_retrospectives.py` | 固定 DDL 增量迁移；保留 B01–B05 数据 |

| 表 | 实际约束与用途 |
|---|---|
| `retrospectives` | 模式、项目范围、来源组键唯一、当前版本及并发版本号 |
| `retrospective_revisions` | 版本、固定来源、指纹、模板/适配器、摘要/时间线/发现/建议；父对象+版本唯一、生成指纹唯一；人工修订不占生成去重键 |
| `retrospective_sources` | 每版的包或历史版本关系；两类来源恰选其一，有真实外键，供撤回过滤 |
| `retrospective_evidence` | 固定事件、任务快照、受控附件、历史行；每版+引用唯一，不伪造 B02 风险记录 |
| `retrospective_experience_conversions` | 同复盘版本+知识类型只转一次；关联真实知识草稿 |
| `knowledge_items` 扩展 | 历史来源或复盘来源恰选其一，保留各自外键；原 B03 数据不改写 |
| `knowledge_evidence_links` 扩展 | B02 证据或复盘证据恰选其一，仍有真实外键 |
| `review_actions` 扩展 | 沿用原审核流水，以 object_type 区分知识/复盘，领域服务校验对象及准确版本。多态对象ID不再挂单一知识外键 |

知识审核、证据打开、发布构建、知识库、混合检索均复用 B03/B04 的路径。两条检索通道在排名前过滤不可用来源，引用打开再次检查权限和来源。后台进程也加载 B06 来源元数据，防止旧知识生成因新增外键未注册而中断。

## 实际接口（内部前缀 `/api/v1`）

| 方法 / 路径 | 行为与版本要求 |
|---|---|
| `GET /retrospectives/template` | 返回演示模板及其适用期限规则 |
| `POST /retrospectives` | `mode=task_process` + `task_package_id`，或 `mode=historical_case` + `record_version_ids`；固定模板版本；返回ID、版本和replayed |
| `GET /retrospectives?mode=&state=&limit=&cursor=` | 授权范围内清单；加工/审核权限 |
| `GET /retrospectives/{id}?revision_id=` | 当前或指定历史版本、证据、版本与审核轨迹 |
| `PATCH /retrospectives/{id}/draft` | revision_id、row_version、reason、summary、findings、suggestions；时间线不接受人工覆盖；保存新版本 |
| `POST /retrospectives/{id}/submit-review` | 准确版本、并发版本及理由；进入原统一审核流程 |
| `GET /reviews?object_type=retrospective_revision&state=pending_review` | 复用审核待办，按审核范围过滤后分页 |
| `POST /reviews/{revision_id}/approve`、`request-changes` | 复用原接口，领域分发；批准还需 evidence_checked=true 和逐项确认 |
| `POST /retrospectives/{id}/publish-experiences` | 当前已批准复盘版本、并发版本、reason、知识类型；只返回 draft_ids，重复调用复用草稿 |

发现条目含 id/type/text/claim_kind/event_refs/evidence_refs/review_state，可附 record_status。证据ID为 B06 证据 UUID；原始事件ID保持不变并与定位对应。所有写操作沿用项目授权、审计与统一错误响应。

B00机器合同无需变更。B05 状态响应的 `retrospective_id` 在该包对应当前复盘后返回ID；未生成或包已撤回为null。生成新包复盘产生新版本，不复用旧审核结论。真实 A 的服务身份、组织/项目映射、取件协议仍为 proposed。

## 版本、重跑与失效

同一任务流和模板复用复盘父对象。重复生成相同来源指纹返回当前人工修订，不能覆盖人改内容；新包产生新草稿，旧版内容与审核结论保留。人工编辑保存新版本，旧版审核不能批准新版。历史案例按固定版本集合分组；更换历史版本集合会形成另一组案例。

读、修改、提交、批准、转换和知识发布均实时核查固定来源。B05 撤回在同事务中标记 B06 的实时失效策略已生效，`pending_consumers` 只保留 B07；不宣称已完成 B07。旧通知若仍含 B06，在线保护同样生效，未实现独立历史通知补扫器。已经下载的文件无法远程追回。

迁移升级不删除原资料；downgrade 在存在 B06 复盘时明确拒绝，要求先显式导出/处理领域数据，避免静默丢失审批成果。不能用降级作为清理数据手段。
